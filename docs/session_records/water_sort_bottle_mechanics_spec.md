# 智力倒水游戏：瓶子机制开发规范

> 版本：V1.0  
> 用途：供 AI 编程助手、客户端开发、规则引擎与 Solver 开发使用。  
> 范围：普通瓶、空瓶、遮罩瓶、隐藏瓶、底部漏水瓶。

## 1. 目标与基本原则

实现一套可扩展、可测试、可被 Solver 搜索的倒水规则系统。必须遵守：

1. 规则状态与动画表现分离。
2. 所有液体变化由规则引擎提交，动画只负责表现。
3. `layers` 是液体的唯一真实数据来源。
4. 所有模块统一使用“底部到顶部”的数组顺序。
5. 隐藏液体仍然存在，隐藏只影响玩家可见信息。
6. 每关通过数据配置特殊瓶规则，不将阈值和瓶子关系硬编码到 UI。
7. Solver 与游戏共用同一套合法性规则。

## 2. 术语与全局规则

### 2.1 术语

- 液层：一格液体，是最小操作单位。
- 顶部液层：瓶口方向最上方的一格。
- 底部液层：瓶底方向最下方的一格。
- 容量：瓶子最多容纳的液层数，默认 4。
- 完成瓶：默认指装满、所有液层颜色相同，且被配置为计入目标的瓶子。
- 遮罩阈值：完成指定数量的目标瓶后，遮罩瓶掉落的门槛。
- 隐藏层：真实存在但颜色暂时不向玩家显示的液层。

### 2.2 液层数组约定

数组统一采用**底部到顶部**顺序：

```js
// 底部蓝色，中间绿色，顶部红色
layers: ["blue", "green", "red"]
```

- `layers[0]` 为底部。
- `layers[layers.length - 1]` 为顶部。
- 普通倒水从数组末尾移除。
- 底部漏水从数组开头移除。
- 渲染层必须遵守该约定，禁止自行反转逻辑含义。

### 2.3 普通倒水规则

玩家选择源瓶 A，再选择目标瓶 B：

1. A、B 不可为同一瓶。
2. A 不可为空。
3. B 必须有剩余容量。
4. B 为空，或 B 顶部颜色与 A 顶部颜色相同，才允许倒入。
5. 一次尽可能倒出源瓶顶部连续同色液层，受目标剩余容量限制：

```js
amount = Math.min(
  countConsecutiveTopColor(source),
  target.capacity - target.layers.length
);
```

6. 无效操作不改变任何逻辑状态，也不计步。
7. 一次成功倒水计 1 步，不按液层数量计步。
8. 如果目标瓶顶部颜色不匹配、目标瓶已满或源瓶为空，拒绝操作。
9. 隐藏瓶必须额外遵守“玩家不能利用未知颜色获得不合理操作优势”的限制，详见第 4 节。

### 2.4 空瓶规则

空瓶默认是普通容器的空状态：`layers.length === 0`。

- 空瓶可以接收任意颜色。
- 空瓶被倒入后成为非空瓶。
- 瓶子倒空后重新成为空瓶。
- 如果关卡编辑器需要区分“初始空瓶”，可以用 `type: "empty"` 标注，但运行时仍遵循普通容器规则。
- 除非关卡明确规定，否则空瓶不应被设计成只能使用一次。

### 2.5 默认胜利条件

建议默认规则：

- 所有参与目标的颜色均完成分类；
- 完成瓶通常要求装满且为单一颜色；
- 空瓶允许保留；
- 隐藏瓶按真实液体判断，不能因颜色未显示就跳过；
- 遮罩瓶底部颜色的预览不代表已完成；
- 底部漏水是可选机制，除非关卡指定，否则不要求必须使用。

项目若采用不同胜利条件，应写入关卡配置并让 Solver 使用同一条件。

## 3. 瓶子类型

### 3.1 普通瓶 `normal`

- 默认容量 4。
- 可以从瓶口倒出，也可以从瓶口接收液体。
- 无遮罩、隐藏或底部漏水能力。
- 可以为空。
- 视觉：透明玻璃、清楚的液层分界、玻璃边缘高光与底部折射。

### 3.2 空瓶 `empty`

空瓶默认只是初始为空的容器。若保留独立类型标签，类型不改变它的普通倒水能力。容量仍由 `capacity` 决定。

### 3.3 遮罩瓶 `masked`

**核心机制：** 瓶身上部被布罩遮挡；底部最下面一层颜色可以隐约显示。达到每关单独配置的完成瓶数量后，布罩掉落。

#### 3.3.1 配置字段

- `maskRevealed`：布罩是否已掉落。
- `unlockTargetCompletedBottles`：该瓶解锁所需的完成瓶数量。
- `countsTowardObjective`：该瓶是否计入目标完成瓶数量。

每个遮罩瓶可以有不同阈值。例如 A 瓶需完成 1 个目标瓶，B 瓶需完成 3 个目标瓶。

#### 3.3.2 完成瓶计数

默认一个完成瓶满足：

```js
layers.length === capacity &&
layers.every(color => color === layers[0]) &&
countsTowardObjective === true
```

完成瓶数量必须从规则状态计算，不可由 UI 动画或显示状态判断。

#### 3.3.3 解锁时机

每次成功的普通倒水或底部漏水提交后：

1. 更新液层。
2. 重新计算完成瓶数量。
3. 检查所有未解锁的遮罩瓶。
4. 若完成瓶数达到该瓶阈值，设置 `maskRevealed = true`。
5. 播放布罩掉落动画。
6. 特殊动画结束后再开放下一次玩家输入。

阈值为 0 时，关卡初始化即解锁。已经解锁的遮罩瓶不能重复播放掉落动画。

#### 3.3.4 可见信息

- 未解锁时，底部液层可显示低饱和、低透明度的预览色。
- 其他被遮挡液层的真实颜色不得通过 UI、提示或普通玩家日志泄露。
- 布罩只改变可见性，不改变液层、容量和合法倒水规则。
- 阈值超过本关理论上可能完成的目标瓶数量时，应报告关卡配置错误。

#### 3.3.5 动画建议

布料从瓶口或瓶身向下滑落，带轻微弹跳；瓶子出现短暂高光或星尘。建议时长 350–600 ms。

### 3.4 隐藏瓶 `hidden`

**核心机制：** 容量默认 4；最多 3 层颜色隐藏；至少保留一层可见。上层液体被倒出后，下一层按顺序揭示。

#### 3.4.1 状态字段

建议用 `hiddenTopLayers` 表示顶部连续隐藏的液层数量：

- `0`：所有液层可见。
- `1`：顶部 1 层颜色隐藏。
- `3`：顶部 3 层颜色隐藏，底部层可见。

必须满足：

```js
0 <= hiddenTopLayers
hiddenTopLayers <= Math.min(3, layers.length - 1)
```

空瓶的 `hiddenTopLayers` 必须为 0。

#### 3.4.2 逐层揭示

普通倒水完成后：

1. 按真实颜色提交液层变化。
2. 计算实际移除的液层数 `amount`。
3. 执行 `hiddenTopLayers = Math.max(0, hiddenTopLayers - amount)`。
4. 重新渲染可见状态。
5. 对新显示的层播放雾气散开或颜色渐显动画。

**公平性限制：** 隐藏层的真实颜色参与规则校验，但玩家不能看到它。为避免玩家一次操作意外倒出多个未知颜色层，普通倒水的可见可操作数量应限制为顶部连续、玩家已知的同色层数量，并且不能跨过未知层。若顶部可见层下面就是隐藏层，则本次最多倒出顶部已知连续层。

如果设计者希望允许按真实颜色连续倒出隐藏层，需要在关卡规则中明确说明这属于“盲倒”机制，并在 UI 中提前告知玩家。

#### 3.4.3 显示规则

- 隐藏只影响颜色显示，不代表空格。
- 目标瓶颜色匹配、容量和胜利判断使用真实颜色。
- 操作失败时显示中性反馈，例如“无法倒入”，不要提示“隐藏层颜色不同”。
- 隐藏层在关卡初始化时固定，不可每次渲染随机生成。
- 隐藏瓶倒空后，隐藏计数归零。

视觉建议：局部磨砂、半透明问号或柔雾，避免整瓶变成不透明黑块。

### 3.5 底部漏水瓶 `bottom_leak`

**核心机制：** 玩家主动点击触发。液体从源瓶底部流向配置的下方目标瓶。目标瓶的**顶部颜色**必须与源瓶底部颜色一致。

#### 3.5.1 交互建议

推荐两步操作：

1. 玩家点击底部漏水瓶，进入选择漏水目标状态。
2. 高亮配置的下方目标瓶，玩家点击目标瓶或专属漏水按钮确认。

若关卡不是严格上下排列，必须通过 `leakTargetBottleId` 指定目标，不能只根据屏幕坐标猜测。

#### 3.5.2 合法条件

所有条件都满足才可漏水：

- 源瓶与目标瓶不同。
- 源瓶至少有 1 层液体。
- 目标瓶未满。
- 目标瓶非空（默认规则）。
- `source.layers[0] === target.layers[target.layers.length - 1]`。
- 目标瓶是关卡指定的下方目标。
- 两瓶均不处于动画锁定状态。
- 两瓶均满足关卡锁定条件。

由于本规则指定匹配下方瓶顶部颜色，空目标瓶默认不合法。如希望允许漏入空瓶，应添加 `allowLeakIntoEmptyBottle: true` 配置。

#### 3.5.3 漏水数量与状态更新

每次成功漏水只移动 1 层：

```js
const color = source.layers[0];
source.layers.shift();
target.layers.push(color);
```

- 成功漏水计 1 步。
- 成功漏水次数 `bottomLeakUses` 加 1。
- 失败不计步、不改状态。
- 漏水后重新检查完成瓶、遮罩解锁与胜利条件。
- 漏水不触发普通瓶口倒水。
- 隐藏瓶的逐层揭示只在其顶部液层被移除时触发，不因底部漏水而触发。

#### 3.5.4 视觉表现

源瓶底部聚液、漏孔高亮、细水柱或水滴向下流，目标瓶液面出现波纹。成功后液层减少/增加一格；失败只播放轻微摇动，不出现液体转移动画。建议时长 350–600 ms。

## 4. 数据结构建议

以下 TypeScript 为示意，可按项目语言转换：

```ts
type ColorId = string;

type BottleType =
  | "normal"
  | "empty"
  | "masked"
  | "hidden"
  | "bottom_leak";

interface BottleState {
  id: string;
  type: BottleType;
  capacity: number;

  // 始终按底部到顶部存储
  layers: ColorId[];

  // 遮罩瓶
  maskRevealed?: boolean;
  unlockTargetCompletedBottles?: number;
  countsTowardObjective?: boolean;

  // 隐藏瓶：顶部隐藏层数
  hiddenTopLayers?: number;

  // 底部漏水瓶
  leakTargetBottleId?: string;

  locked?: boolean;
}

interface LevelRules {
  colors: ColorId[];
  bottles: BottleState[];
  maskUnlockRules: Record<string, number>;
  allowLeakIntoEmptyBottle?: boolean;
  requiredMechanics?: {
    bottomLeakUses?: number;
  };
}

type GamePhase =
  | "idle"
  | "selected"
  | "pouring"
  | "leaking"
  | "revealing"
  | "mask_falling"
  | "won";

interface GameRuntimeState {
  bottles: BottleState[];
  selectedBottleId: string | null;
  selectedLeakSourceId: string | null;
  steps: number;
  bottomLeakUses: number;
  phase: GamePhase;
}
```

约束：

- `layers` 是唯一液体真值，不要同时维护互相冲突的液量变量。
- `maskRevealed`、`hiddenTopLayers`、步数和漏水次数必须进入撤销快照。
- UI 不得自行决定操作是否合法。
- 规则校验应尽量写成纯函数，方便 Solver 与单元测试调用。

## 5. 操作流程与优先级

### 5.1 普通倒水

```text
选择源瓶
  → 校验源瓶可操作且非空
  → 选择目标瓶
  → 校验容量、颜色、锁定与隐藏瓶限制
  → 计算可倒出的顶部连续同色数量
  → 保存撤销快照并提交状态
  → 播放普通倒水动画
  → 更新隐藏瓶揭示状态
  → 重新计算完成瓶
  → 检查遮罩瓶解锁
  → 检查胜利条件
  → 回到 idle
```

### 5.2 底部漏水

```text
选择漏水源瓶
  → 取得配置的下方目标瓶
  → 校验源瓶底部色与目标瓶顶部色
  → 校验容量、非空、锁定状态
  → 保存撤销快照并移动 1 层
  → 漏水动画
  → 步数和漏水次数更新
  → 重新计算完成瓶
  → 检查遮罩解锁
  → 检查胜利条件
  → 回到 idle
```

### 5.3 原子事务

- 校验失败：状态完全不变。
- 校验成功：一次性提交状态变更。
- 提交后生成动画事件。
- 动画回调不能重复提交同一操作。
- 动画中断时，表现层应重新同步到当前规则状态，不得重复倒水。
- 所有特殊事件按队列串行处理，避免同一瓶子被多个动画同时修改。

## 6. 状态机

| 状态 | 含义 | 输入策略 |
|---|---|---|
| `idle` | 等待玩家操作 | 可选择普通瓶或漏水瓶 |
| `selected` | 已选择普通倒水源 | 可选目标或取消 |
| `pouring` | 普通倒水动画 | 暂停瓶子输入 |
| `leaking` | 底部漏水动画 | 暂停瓶子输入 |
| `revealing` | 隐藏层揭示动画 | 暂停瓶子输入 |
| `mask_falling` | 布罩掉落动画 | 暂停瓶子输入 |
| `won` | 已通关 | 只允许通关界面操作 |

转移规则：

```text
idle --选择普通瓶--> selected
selected --合法目标--> pouring
selected --再次点击源瓶--> idle
selected --无效目标--> selected（轻反馈）
pouring --无后续事件--> idle
pouring --揭示隐藏层--> revealing --> idle
pouring --遮罩解锁--> mask_falling --> idle
idle --合法漏水操作--> leaking
leaking --无后续事件--> idle
leaking --遮罩解锁--> mask_falling --> idle
任意操作结束 --满足胜利条件--> won
```

一次操作可能依次触发“倒水、揭示、遮罩掉落、胜利”。事件必须串行执行，建议事件名：`PourCommitted`、`LeakCommitted`、`HiddenLayerRevealed`、`MaskUnlocked`、`BottleCompleted`、`LevelWon`。

## 7. 动画与反馈规范

下列时长是初始建议值，需在目标设备上调优。

| 事件 | 建议时长 | 表现 | 逻辑要求 |
|---|---:|---|---|
| 选中瓶子 | 120–180 ms | 上浮、轻微放大、高光 | 不改液体 |
| 无效操作 | 160–240 ms | 轻微摇动 | 状态不变 |
| 普通倒水 | 450–750 ms | 倾斜、弯曲水柱、液面上升 | 操作只提交一次 |
| 液面稳定 | 120–220 ms | 波纹衰减、少量气泡 | 纯表现 |
| 隐藏层揭示 | 250–450 ms | 雾气散开、颜色渐显 | 不改变真实颜色 |
| 布罩掉落 | 350–600 ms | 布料下滑、轻微弹跳 | 解锁只执行一次 |
| 底部漏水 | 350–600 ms | 底部聚液、水滴/细水柱、目标波纹 | 每次只移动一层 |
| 通关 | 500–900 ms | 完成瓶轻弹、少量星光 | 胜利事件只触发一次 |

### 7.1 液体表现要求

- 液体必须贴合瓶内轮廓。
- 水柱颜色来自实际流动液层。
- 普通倒水时源瓶液面按实际移除数量降低。
- 隐藏颜色不得提前显示。
- 底部漏水从瓶底向下，不能复用瓶口旋转倒水表现。
- 动画期间可使用临时表现液量，但结束后必须与规则状态一致。

## 8. 边界条件与异常处理

### 8.1 普通倒水

- 空源瓶：拒绝。
- 同一瓶作为源和目标：取消选择或轻反馈。
- 目标已满：拒绝。
- 颜色不匹配：拒绝。
- 目标只剩 1 格空间：最多倒 1 格。
- 顶部连续同色 3 格、目标剩 2 格：倒 2 格。
- 动画锁定期间点击：忽略，不缓存重复操作。

### 8.2 遮罩瓶

- 阈值为 0：初始化时解锁。
- 阈值不可达到：关卡配置警告。
- 一次操作使完成瓶数跨过多个阈值：所有满足条件的遮罩瓶依序解锁。
- 已解锁的瓶子不可重复掉罩。
- 遮罩瓶倒空是否触发解锁由目标完成定义决定；建议仅按完成瓶计数解锁。
- 底部预览颜色不应泄露其他液层。

### 8.3 隐藏瓶

- 空瓶隐藏计数必须为 0。
- 隐藏层数不能超过液层数减 1（默认至少一层可见）。
- 移除液层后隐藏计数不能小于 0。
- 颜色匹配与胜利判断使用真实颜色。
- 玩家提示不得直接泄露未知颜色。
- 单次操作不能跨过未知层，除非关卡明确采用盲倒规则。

### 8.4 底部漏水

- 源瓶为空：拒绝。
- 目标瓶为空：默认拒绝。
- 目标瓶已满：拒绝。
- 源瓶底色与目标瓶顶色不匹配：拒绝。
- 目标不是配置的下方瓶：拒绝。
- 动画中重复触发：忽略。
- 失败不计步、不增加漏水次数、不改液层。

### 8.5 撤销与重置

撤销快照至少包含：

- 所有瓶子的液层；
- 遮罩状态；
- 隐藏层数量；
- 步数与漏水次数；
- 影响合法操作和胜利判断的关卡状态。

撤销时停止动画、清空事件队列、恢复完整快照并重新渲染。重置恢复关卡初始状态。若关卡包含随机机制，应恢复初始随机种子。

## 9. 关卡配置示例

```json
{
  "levelId": "level_001",
```

## 10. Solver 约束与求解策略

### 10.1 Solver 状态

Solver 状态必须包含所有影响后续合法动作与胜利判断的数据：

```ts
interface SolverState {
  bottles: {
    id: string;
    type: BottleType;
    capacity: number;
    layers: ColorId[];
    maskRevealed?: boolean;
    hiddenTopLayers?: number;
  }[];
  steps: number;
  bottomLeakUses: number;
}
```

遮罩解锁进度可由瓶子状态重新计算，也可存入状态，但必须确保哈希状态完整且一致。

### 10.2 合法动作生成

**普通倒水动作：**

1. 遍历所有非空源瓶 A 与不同目标瓶 B。
2. 检查容量、顶部颜色、锁定状态与隐藏瓶限制。
3. 计算顶部连续同色数量和目标剩余容量。
4. 移动允许的液层。
5. 更新隐藏瓶揭示状态。
6. 重算完成瓶数量。
7. 更新遮罩瓶解锁状态。
8. 检查胜利条件。

**底部漏水动作：**

1. 仅为支持底部漏水的瓶子生成动作。
2. 目标只能是配置允许的下方瓶。
3. 源瓶非空，目标瓶非空且有容量。
4. 源瓶底部颜色必须等于目标瓶顶部颜色。
5. 每次只移动一层。
6. 更新步数、漏水次数、完成瓶与遮罩解锁。
7. 检查胜利条件。

### 10.3 真实状态与玩家观察状态

必须区分：

- **真实状态**：所有液层颜色均可见于规则引擎和关卡验证器。
- **观察状态**：仅包含玩家当前被允许看到的颜色。
- **验证 Solver**：可以使用真实状态，判断关卡是否存在解。
- **提示 Solver**：必须遵守观察状态，不能泄露隐藏颜色，除非消耗了明确的揭示道具。

### 10.4 搜索算法

- 小关卡：BFS 可寻找最少步数解。
- 中大型关卡：A*、IDA* 或带启发式的 DFS。
- 使用状态哈希去重，防止循环。
- 可对完全等价的普通瓶排序规范化；不能交换具有不同解锁阈值、隐藏状态或指定漏水目标的特殊瓶。
- 设置节点上限和超时；预算耗尽时返回“未在预算内找到解”，不能直接断言无解。
- 只有使用可证明最短路径的算法完整搜索后，才能标记“最优步数”。

启发式可以考虑颜色分散程度、瓶内颜色切换次数、待解锁遮罩瓶、漏水条件准备成本等。若 A* 要保证最优，启发式必须满足可采纳性。

### 10.5 Solver 验收

- 同一关卡与规则版本可复现。
- 每一步都通过正式规则引擎校验。
- 返回路径实际执行后必须到达胜利状态。
- 游戏内提示不泄露隐藏颜色。
- 遮罩解锁、隐藏揭示和底部漏水均纳入状态与哈希。
- 不可将任意可行解直接标记为最优解。

## 11. 验收用例

### 普通倒水

1. 源瓶顶部连续 3 格红色，目标顶部红色且剩 2 格：只倒 2 格。
2. 源瓶红、目标顶部蓝：拒绝且状态不变。
3. 源瓶为空：拒绝。
4. 目标瓶已满：拒绝。

### 遮罩瓶

1. 阈值为 2，完成瓶数从 1 变 2：布罩掉落一次。
2. 完成瓶数继续增长：已解锁瓶不重复播放动画。
3. 阈值不可达到：关卡校验报错。
4. 未掉罩时只显示底部预览色。

### 隐藏瓶

1. `hiddenTopLayers = 2`，顶部移除 1 格后变为 1，下一层显露。
2. 移除层数不得让隐藏计数小于 0。
3. 隐藏颜色仍参与真实规则，但不能被普通提示泄露。
4. 空瓶隐藏计数为 0。

### 底部漏水

1. 源瓶底色为绿、目标瓶顶色为绿且有空间：成功漏入 1 格。
2. 两种颜色不匹配：拒绝。
3. 目标为空或已满：按默认规则拒绝。
4. 目标不是配置的下方瓶：拒绝。
5. 成功时步数和漏水次数各加 1，失败时均不变。

### 状态与动画

1. 动画中连续点击不会生成额外动作。
2. 动画结束后渲染与逻辑数组一致。
3. 撤销恢复液层、遮罩、隐藏计数、步数和漏水次数。
4. 重置恢复关卡初始状态。
5. 一次操作不能重复触发布罩掉落或胜利事件。

## 12. 建议开发顺序

### 阶段一：基础规则
普通瓶、空瓶、连续同色倒水、校验、步数、撤销、重置、胜利判断。

### 阶段二：特殊状态
遮罩瓶阈值、隐藏瓶逐层揭示、底部漏水主动操作、统一事件队列。

### 阶段三：动画
玻璃和液体渲染、瓶口水柱、液面波纹、布罩掉落、隐藏层揭示、瓶底漏水。

### 阶段四：Solver
基础 Solver → 遮罩状态 → 隐藏层真实/观察状态 → 底部漏水动作 → 自动关卡验证。

### 阶段五：质量验证
运行全部验收用例，测试连点、动画中断、撤销、重置、设备性能和每关可解性。

## 最终开发原则

- **规则是唯一真相**：UI 和动画不决定操作合法性。
- **数组顺序统一**：所有模块使用底部到顶部。
- **隐藏不等于不存在**：隐藏颜色仍参与真实规则。
- **关卡数据驱动**：阈值、瓶子位置和漏水关系都由配置定义。
- **特殊事件串行处理**：先提交操作，再揭示、解锁、判断胜利。
- **Solver 与正式规则共用逻辑**：避免提示与实际游戏行为不一致。
- **视觉反馈不泄露信息**：隐藏瓶的提示必须遵守玩家可见信息边界。
